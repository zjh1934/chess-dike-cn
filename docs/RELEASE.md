## v1.21 更新内容（回到原作者：3 帧认准棋盘 + 一次完整算完才念）

按用户要求，把上游 `Silva6c/chess-dike` v3.4 的 `RecognitionTypes.kt` / `ScreenAssistService.kt` 只读参考逐行读进上下文，对照 10:44 诊断（600 行 / 26 次点按）重做。

### 用户这轮的三条要求

1. 「他怎么保证准确棋盘现状，他识别几次咱就识别几次」→ 原作者 `BoardTracker(confirmCount = 3)`：**连续 3 帧逐格一致**才确认，另有子数跳变门限（真实走子只 ±1，噪声 ±2~3）挡动画/幻觉帧
2. 「他怎么获得更好的支招，他计算几次咱就计算几次」→ 原作者每确认一个局面只 `analysisEngine.request(fen)` **一次**，等 `onSearchDone` 的 bestmove 才把建议标「定着 ✓」
3. 「如果对方走什么我方可走什么这种不要计算」「我是红就别算黑」→ 上游自带的空闲预计算 β（`PonderCache` / `lastPreFen` / 「若对方走X 我方应Y」预案行）**整块删除**；`!myTurn` 不发任何引擎请求

### 10:44 日志暴露的两个新问题

| 现象 | 数据 | 根因 |
| --- | --- | --- |
| 「定着✓」来得太快 | 12 次标 `定着✓ 深20` 却只等 **27~239ms**，而正常深度 20 要 1~2 秒 | 残留/缓存 bestmove 冒充本轮定着；`suggestMature = searchSettled \|\| 稳定1200ms` 也会把没算完的 PV 当成熟 |
| 同一招连念 9 次 | 「车二进八」在 10:31:07~10:32:26 念了 9 次 | 同一局面反复点按，YOLO 每帧抖动导致 FEN 看着变了，重复判定失效；叠加残留定着 0.2 秒就给同一招 |

v1.20 的「1 秒质量窗口 + 深≥8 截念暂定 PV」虽比 v1.16 深，但**仍是没算完的着法**：13/25 次念的是「（暂定）」。

### 这版怎么做

- **识别**：新建 `TapConfirm3`（纯 JVM），连续 3 帧 `AssistBoard.equal` 一致才建局；中间插一帧不同局面就从 1 重新累计；`pieceJumpPlausible` 照搬原作者 `tol = max(2, 已确认子数/10)`。抓帧窗口放宽到 8 帧 / 1.4 秒，**不查节拍器、不等帧差、不等停稳** —— 点击后立即连续重提交帧，正常 3 帧约 0.4~0.6 秒，不回到 v1.11 的 6~12 秒。每帧仍走数量规范化（含 v1.20 延续性加成）把 YOLO 抖动就地修好
- **支招**：`scheduleAnalysis` 只在我方回合发**唯一一次**完整搜索；`TapSpeakGate` 收紧为「只认 `mature=true`」—— 本轮 `onSearchDone` 的 bestmove 定着 ✓、或开局库库着；中间 info 行的暂定 PV 一律不念。`renderOverlay` 的 `suggestMature` 也只认 `searchSettled`，不再用「稳定 1200ms」放水
- **防冒充**：新增 `tapSearchRequested` 本轮标记。`onSearchDone` 只有「本轮确实发过搜索 + 会话还开着 + FEN 对得上」才置 `searchSettled=true`，否则写「忽略非本轮/残留 bestmove」。10:44 那 12 次 27ms 假定着和连念同一招就此断根
- **删掉的两种计算**：`ponderCache.pick/feed`、`lastPreFen`、`precomputeHit` 命中路径、`setPrecomputeEnabled` 固定关、`!myTurn` 的 request、以及「若对方走X 我方应Y」预案行。`AnalysisEngine` 本身没有 `go ponder`，发的就是 `go depth N` / `go movetime X` 一次
- **日志不再冒功**：小票「点击→播报」原记的是「点击→箭头出现」（10:44 里 0.17s 而真实 1.16s），改成真正把着法交给 TTS 的时刻；「④ 箭头已画出 → 立刻进入播报」这句老文案改掉；新增「确认帧数」「本轮定着」行；硬预算强制定着时「招法质量」如实写「硬预算·未定着」
- **延迟**：3 帧确认约 0.4~0.6 秒 + 完整搜索通常 1~2 秒；硬预算从 2.5 秒放宽到 **3 秒**给 bestmove 留时间，到点必有声音、绝不静默

### 取舍（如实说）

- 出声会比 v1.20 慢一点：以前 1 秒窗口截念，现在必须等本轮 bestmove。这是用户「按原作者的来，他计算几次咱就计算几次」的明确要求；3 秒硬预算保证不会无限等
- 3 帧确认在极端静止 ROM 上若凑不齐，会语音提示「画面没认稳，再点一次棋盘」，不静默、不拿单帧赌
- 硬预算到点强制定着念的是当前最佳着（可能不是最终 bestmove），日志会标明「未定着」，不冒充
- 重复点按重念上一招的逻辑保留；3 帧确认把识别抖动压下去后，连念 9 次同一招的情况会明显减少

### 没动的部分

TTS 出声回执自愈、日志不冒功、数量规范化 + 延续性、点击擦旧箭头、固定 YOLO、固定签名 + 指纹硬门禁、面板红黑互斥锁定、起点双保险、本轮只念一招、一键关录屏、极简 Release 正文。**v1.20 直接覆盖安装。**

## v1.20 更新内容（支的招不再馊：等算稳才念 + 裁剪别丢错真子）

07:58 诊断（v1.19，600 行 / 28 次点按，含跨会话历史）逐条算完，也把引擎调度、PV 更新、播报门控、YOLO 映射层全读进上下文了。

### 先摆数据：语音和延迟其实都好了，问题在招本身

| 指标 | 实测 |
| --- | --- |
| 点按成功出声 | **28 / 28（100%）**，朗读回执「onStart 已出声✓」28 次 |
| 点击→播报 | 最快 186ms、最慢 584ms、**平均 322ms** |
| 念的着法质量 | **28 次全是「（暂定）」，0 次「定着✓」** |
| 重复着法 | 炮1退1、卒7进1、卒1进1、炮6进7、车3平1 各念了 2 次；seq=115/116 隔 8 秒两次都是「炮1退1」 |
| 画面被裁子 | **10 / 28（36%）**：象×1 五次、帅×1 三次、一次裁 2 子三次 |

所以这次不是「不读」「不响应」「掉线」，是**念得又快又勤，但念的是浅算的招**。

### 根因一：念的是引擎第一条浅 PV（主因）

`TapSpeakGate` 自 v1.16 起把播报挂在「箭头画出来」那一刻。而 `renderOverlay` 的箭头来自 `onSearchUpdate` —— 引擎每来一条 info 行就刷新一次界面，**第一条 info 通常只有 depth 1~4**；真正的 `bestmove`（`onSearchDone` → `searchSettled=true`）要 1~2 秒才到。v1.16 为了用户「算出来就要给我读」把 1.2 秒定着等待砍了，结果 28/28 全念在最浅那一层。日志里每一条 `⑤ 语音播报` 的文案都带「（暂定）」，就是铁证。

**v1.20 做法（不退回秒级干等）**：
- `TapSpeakGate.decide` 新增质量参数：`mature`（定着✓ / 开局库 / 预判β / 稳定 1200ms）→ **立刻念，零等待**
- 其余等 **1 秒短质量窗口**且当前 PV 深度 ≥ 8 才念
- 建局后挂 `tapQualityTick`，窗口到点强制重渲染做判定，引擎没新 info 也不会卡住
- **2.5 秒硬预算**：到点强制定着、用当前最佳着念一次；250ms 后仍没念就语音提示，绝不静默

用户要的「最多两三秒出声」仍成立：定着常在 1~2 秒到，最差 2.5 秒兜底。日志新增「招法质量」行，写明来源、深度、等招算稳耗时，以后一眼验证还在不在念浅招。

### 根因二：裁剪可能丢错真棋子

v1.18 的 `PieceLimitTrim` 只按置信度丢「数量超上限」的多余者。07:58 日志里 10 次被裁子，其中 3 次裁的是「帅×1」、3 次一次裁 2 子。万一某个**真棋子**这帧分数偏低、而背景误检分数偏高，就会丢错真子 → 引擎按缺子/错子的局面算 → 搜得再深也是馊主意。

**v1.20 做法**：把上一帧的 canonical 局面还原成屏幕坐标系传进裁剪器。某个候选格若上一帧同位置就是同样的棋子，给一个 `CONTINUITY_BONUS=2.0` 的延续性加成分数（置信度域 0..1，足够压过分数抖动）；背景误检上一帧通常不存在，于是优先被丢。不增加任何等待、不叫用户重点。日志「数量规范化」行追加「延续性保住 N 个真子」。

### 根因三：同一局面重复点按会重新浅算

`applyTapDirectBoard` 每轮都 `tracker.redGo = myRed` 并 `scheduleAnalysis()`。棋盘没变（常见于又点了一下，或 YOLO 漏检了新落子）时，引擎会按「我方又走一步」重算，招法自然越支越离谱；日志里 seq=115/116 隔 8 秒两次都念「炮1退1」就是这情况。

**v1.20 做法**：记录上一轮局面 FEN 与念过的纯中文着法；新帧 FEN 完全相同就**重念上一招**、写「重复点按」行、直接收场，不重建局面、不重新搜索。

### 取舍（如实说）

- **延迟会变大**：从平均 0.32 秒变成约 1~2 秒（等定着或深 PV）。这是「招法质量」换来的，用户明确说「馊主意」比「慢一点」更不能接受；2.5 秒硬预算保证不会无限等。
- 若引擎在 1 秒时深度仍 <8，会继续等到 2.5 秒硬预算，此时念的是「强制定着」的当前最佳着 —— 日志「招法质量」会如实写明来源，不冒功。
- 延续性加成假设「上一帧在场的真棋子这帧大概率还在」；刚被吃、刚移动的子不享受加成，仍按置信度处理，属于少数情况。
- 重复局面判定基于 FEN 完全相同；若识别漏检导致「其实变了但看起来没变」，会重念上一招。这比按错轮次给一招新馊主意更稳妥，且日志会写明。

### 没动的部分

TTS 出声回执自愈、日志不冒功、数量误检就地修、点击擦旧箭头、单帧直出、2.5s 硬预算、固定 YOLO、固定签名与指纹硬门禁、面板红黑互斥锁定、起点双保险、本轮只念一招、一键关录屏、极简 Release 正文 —— 全部保留。**v1.19 直接覆盖安装。**

### 打包前门禁新增 3 组

招法质量门槛（定着零等待 / 浅 PV 要等深 / 横跳防线仍在）、裁剪延续性（真子保住、误检被丢、坐标互逆）、服务层接线（质量参数 / 招法质量日志 / 重复局面重念 / 上一局面透传）—— 全绿才准出包。

## v1.19 更新内容（切红黑后不读：不是切换的锅，是 TTS 掉线 + 日志冒功）

对着 03:26 诊断（600 行 / 19 次点按，含跨会话历史）逐行核对，把 `VoiceSpeaker`、链路日志、状态文案、切换处理全读进上下文了。**先回答你问的那句：不是切换红黑导致的。**

### 时间线：切换之前语音就已经哑了

| 时刻 | 发生了什么 |
| --- | --- |
| 03:19:39 ~ 03:21:40 | 12 次朗读全部完整：`决策` → `打断` → `speak SUCCESS` → `onStart` → `onDone` |
| **03:21:47.919** | 最后一次 `speak SUCCESS：车六进二`，**但连 onStart 都没有** —— 系统已经没出声 |
| 03:21:54 ~ 03:24:59 | 12 次 `决策` + `打断` 全打齐，**再没有一条 speak SUCCESS / onStart / onDone**；也没有失败日志 |
| 03:25:37 ~ 03:25:44 | 我方=黑（悬浮面板手动锁定），7 次点按**连「决策」行都没有**，链路却仍写「⑤ 语音播报」「已出招·已播报」 |

红黑切换发生在 03:25 段，而 TTS 在 **03:21:47** 就不出声了。所以「切了才不读」是时间上的巧合，切换只是你注意到它的时间点。

### 三个根因

**1. 只看「调用返回成功」，不看「系统有没有真出声」**
`VoiceSpeaker.speak()` 过去以 `tts.speak() == SUCCESS` 为终点，但 Android 的 TTS 服务连接被系统回收后，这一层完全可能既不返回 SUCCESS、也不抛异常、也不回调 `onStart/onDone` —— 程序以为念了，实际一个字没出。`rebuild()` 又只在「换 TTS 引擎包名」时才重建，连接掉线不会自愈。

**2. `shuttingDown` 是个不可逆的死锁**
`onSuggestion()` 第一行 `if (shuttingDown) return` 静默返回；而 `shutdown()` 只在 `onDestroy` 和 `speakTest` 的 `finishTestIfNeeded` 里调。v1.18 我把失败提示挂在**共享** `voiceSpeaker.speakTest(...)` 上，而 `speakTest` 的契约是「只给独立实例用，读完自行 shutdown」—— 一旦走到，整个支招朗读器就被永久封死，表现就是「连决策行都没有」。（这份日志里 19 次点按全成功，没走到失败提示，但路径确实存在，一并拆掉。）

**3. 日志在冒功**
`⑤ 语音播报` 和 `endTapSession("已出招·已播报")` 都是**无条件**写的，不管 TTS 出没出声。系统哑了 12 次，日志里还是 12 个「已播报」，难怪排障排不出来。这正是你之前强调「日志一点参考价值都没有」的那类问题。

### v1.19 怎么改

- **出声回执看门狗**：`speak` 返回 SUCCESS 后启动 1.5 秒计时，没收到系统 `onStart` 就写「朗读无回执」→ 判定掉线 → 丢弃失效实例 → 重新绑定 TTS → **补念一次**。失败 / 异常 / `onError` 同样处理。
- **朗读前自愈**：`ensureAlive()` 在实例为 null / 已 shutdown / 初始化失败 / `tts==null` 时调 `repair()`，解除 `shuttingDown` 死锁；服务层交稿前必调，并且 `voiceSpeaker` 为 null 时即时重建。
- **失败提示换接口**：新增 `speakNotice()`，不置 `testMode`、不 `finishTestIfNeeded`，不再污染共享朗读器；`speakTest` 保留但只给设置页独立实例用。
- **日志按真实回执写**：没拿到 `onStart` 就写「已出招·已交TTS(待朗读回执)」，绝不写「已播报」；新增「朗读回执 / 朗读无回执 / TTS重建」三类行，切换红黑后一眼看出是 TTS 先掉线还是切换动作。
- **2.5 秒硬预算增强**：已交稿但没回执时，重建朗读器并补念一次纯中文着法，绝不静默。
- **日志降噪**：`状态文案` 在 03:26 诊断里占 **154 / 600 行**，把「我方选择」等关键行挤出了 600 行上限。现在同一句状态 1 秒内不重复写；「我方选择」行加唯一 seq 与时间戳，确保不被聚合掉。

### 取舍（如实说）

- 1.5 秒无回执才判定掉线，极少数慢启动的 TTS 引擎可能触发一次多余重建；重建后会补念，不会丢招。
- 这份日志**没有** `speak失败` / `speak异常` / `onError` 行，系统层到底是连接被回收还是引擎进程被杀，日志无法 100% 确证。所以修法做成防御性的「看回执 → 掉线就自愈」，不依赖猜中系统层原因。
- 「我方选择」事件行在这份导出里一条都没有（被刷屏挤出上限），降噪后下份日志会带出来。

### 没动的部分

数量误检就地修、点击擦旧箭头、单帧直出、2.5s 硬预算、固定 YOLO、固定签名与指纹硬门禁、面板红黑互斥锁定、起点双保险、本轮只念一招、一键关录屏、极简 Release 正文 —— 全部保留。**v1.18 直接覆盖安装。**

### 打包前门禁新增 1 组

TTS 掉线自愈（回执看门狗 / 重建补念 / shutdown 死锁解除 / 失败提示不污染共享实例 / 日志不冒功 / 切换行唯一化 / 状态降噪）—— 全绿才准出包。

### 先摆数据

| 指标 | 实测 |
| --- | --- |
| 点按成功出声 | **8 / 19（42%）**，11 次静默收场 |
| 用户连点间隔 | 1.9 / 2.0 / 2.2 / 2.3 / 2.4 / 2.8 秒密集出现 —— 就是「点了没声音→再点」 |
| 失败原因 | `卒数量超限:6` 11 次、`象数量超限:3` 7 次、`马数量超限:3` 1 次 |
| 「④ 箭头已画出」时机 | **18 / 19 次出现在点击后 2~7 毫秒，比第一帧识别还早** |

抓帧其实不慢（点击→取帧 11~29ms、YOLO 107~219ms），单轮点按小票 290~621ms。**慢的不是取帧，是「取到了却判死、还不吭声」**。

### 根因一：YOLO 多认 1 个子 → 整局判死 → 静默收场

`DetectionBoardMapper.map` 把每个检测 round 到格子，同格冲突保留高分者，**但从不检查每类棋子的总数上限**。YOLO 偶尔把背景或相邻棋子又检成一个卒/象，于是局面里卒=6、象=3 → `AssistBoard.validate` 报「数量超限」→ `TapFrameGate` 一票否决 → 3 帧全废 → 收场，只弹一句「再点一次」，**没有声音**。

v1.16/v1.17 试图靠「再抓几帧 / 两帧一致」绕过，但 `forceCaptureFrame()` 用 `setSurface + resize` 重提交的是**同一静止画面**，YOLO 每帧抖动认出不同的错（日志里 18 次「与上一局面差 4 格疑似误检」、5 次「两帧不一致」、18 次「第一帧合法，再抓一帧确认」），3 帧窗口被吃光后照样收场。方向错了：**该修的是这一帧，不是等下一帧碰运气**。

**v1.18 做法**：象棋每类棋子有硬上限（车马炮仕相各 2、兵卒各 5、帅将各 1），多出来的那个几乎必然是置信度最低的误检。新增 `PieceLimitTrim`（纯 JVM），在映射层按 `cellScore` 升序丢掉超出的，产出合法局面再交给 `validate`。`AssistBoard.PIECE_LIMITS` 改为包内可见作单一真源。就地修，零额外等待。

同时**删掉主链路上的「两帧一致」和「与上一局面一步校验」**（这两个纯 JVM 类保留但不再调用），回到你一直要的「这一帧直接算」。硬致命校验保留：帅/将数量异常、两将照面、未识别格、总子数 >32 —— 这些真的会瞎指挥。

### 根因二：「还在上一步」＝ 点击瞬间画的是旧箭头

`startTapRecognition` 只清了 `tapLockedText`，没清 `lastAnalysis`。于是 `setStatus("正在读取屏幕…")` 触发的 `postRender()` 里，`renderOverlay` 看到旧的 `line != null`，把**上一轮的建议箭头又画了一遍**；而「④ 箭头已画出」的判定只要求 `tapSessionActive`，就在点击后 2~7ms 记下了这条假事件。你点下去看到的还是上一手的箭头，自然觉得「它没去读屏幕」。

**v1.18 做法**：
- 点击瞬间调 `resetSuggestionState()` 清掉旧建议/引擎结果，并立刻 `postRender()` 擦面板
- 「④ 箭头已画出」必须等 `tapSessionAwaitSettle`（本轮已建局）才记
- 日志的「箭头出现→播报」由此从本次真箭头起算，不再被旧箭头污染

### 根因三：失败收场完全静默

11 次失败只有文字提示、没有一句声音。你要的是「最多两三秒就要给我出声音」。

**v1.18 做法**：
- **2.5 秒硬预算**（`TAP_HARD_SPEAK_MS`）：到点还没播报，强制给声音 —— 已建局就强制定着念当前最佳着；还没建局但有合法帧就立刻建局支招；连帧都没有就念「没看清棋盘，再点一次」
- **所有失败收场都走 `endTapSessionWithVoice`**：念一句明确提示，同轮只念一次，绝不静默
- 点按小票新增「点击→播报」总耗时；正常路径约 0.3~0.6 秒

### 日志（按你之前说的「要有参考价值」）

新增「数量规范化」行（裁掉几子、哪类、按置信度丢最低者）、「点击→播报」耗时、硬预算兜底行；排障提示全部改成 v1.18 口径。隐私边界不变：不记画面像素、FEN 内容、对局记录、引擎搜索明细。

### 取舍（如实说）

- 就地裁剪是「按置信度丢掉多余的那个」，极少数情况下若模型把**真棋子**判成低分、把误检判成高分，会丢错一个。但相比「整局判死让用户连点 2~6 次」，这是明显更好的权衡，且日志会把裁了哪类写清楚。

- 未出招时的语音提示是「没看清棋盘，再点一次」，不是支招；裁剪后成功率应大幅上升，这句只在极少数异常时出现。

## v1.17 更新内容（去掉用不了的选项，点棋盘稳定好用）

### 先说这份日志能确证什么

02:19 那份诊断只有 **7 行**，02:19:49 服务启动 → 02:19:53 打开增强功能页 → 02:19:58 导出，**9 秒内没有一条点棋盘记录**（你刚卸载重装过 v1.16，落盘的跨会话历史被清掉了）。所以这份日志不能直接告诉我们「点棋盘哪几次没成」，但它把「两种模式」钉死了：

```

服务onCreate 识别引擎=onnx 确认帧数=3
状态文案     ONNX 引擎加载失败／已回退 YOLO 识别 ｜ 会话=关 闸口=关
```

结合代码与上一份 38 次点按日志，三个现象其实是**两个根因**。

### 根因一：「两种模式」= ONNX / YOLO 识别引擎，第一种永远用不了

连线主页那行「识别引擎」有两个单选：**ONNX 角点式**（配置默认，第一种）/ **YOLO 检测式**（第二种）。ONNX 模型受版权保护不随包分发（`assets/models/*.onnx` 被 .gitignore 排除），于是：

- 每次启动 `initEngine("onnx")` → 模型文件不存在 → **0ms 加载失败** → 运行态回退 YOLO；
- 但 `AssistConfig.recognizerEngine` 里存的还是 `onnx`，连线页 `onResume` 又按运行态回填 RadioGroup → **你选了第一种，它自动跳回第二种**；
- 状态栏一直挂着「ONNX 引擎加载失败／已回退 YOLO 识别」，看着就像没配对。

**更要命的是它顺带把「有时不管用」也解释了**：悬浮面板上那个「引擎」芯片是可点的，点一下就 `switchEngine(onnx)` —— 里面会 `tracker.reset()`、`resetSuggestionState()`、`sessionGrid = null`，而且 ONNX 加载线程还没回来时 `onnxEngine == null`。这时你紧接着点棋盘，识别分支拿到的是「ONNX 未就绪」，3 帧重试全废，只能提示「再点一次」。不是点棋盘坏了，是刚被切引擎清空了状态。

**v1.17 做法（按你一直要的「装上点一下就能用」）**：这个模型永远不会随包出现，选项留着只会害人。直接摘掉——

| 位置 | 改动 |
| --- | --- |
| `AssistConfig` | 读写双向幂等归位 `yolo`，旧值/脏值/外部写入一律按 YOLO 处理 |
| 连线主页 | 单选行只读，ONNX 项隐藏，YOLO 标注「（固定）」，不再注册切换监听 |
| 悬浮面板 | 「引擎」芯片改只读，点击只提示「YOLO（本版固定）」，**绝不再清棋盘状态** |
| 服务 | `initEngine` 不再启动任何 ONNX 加载线程；`setRecognizerEngine` 忽略非 YOLO 请求 |

启动日志不再有「ONNX 加载失败」，状态栏也不再挂着那句失败提示。

### 根因二：「有时瞎指挥」= 第一帧合法就建局，误检帧能混过门槛

v1.16 为了少让你重点，改成「短窗口内**第一帧合法就建局**」。但 `AssistBoard.validate` 只查：帅=1 / 将=1 / 各子上限 / 总数 ≤32 / 两将照面 —— **不查总数下限，也不查这一局面和上一局面对不对得上**。YOLO 漏检两三个子、或者抓到对方走子动画的过渡帧，照样判「合法」，于是按一个不存在的局面支招。原作者的「连续多帧一致」本来就是防这个的。

**v1.17 做法（不等好几秒，只多一帧约 0.1 秒）**：

1. `TapFrameConsensus`：点击后自然到达的帧逐帧比，**连续两帧一致**才采纳；不一致就再抓一帧，最多 3 帧 / 700ms。
2. `TapBoardStep`：窗口用尽仍凑不齐两帧时，用「与上一确认局面是否说得通」兜底 —— 首次点 / 重复点同一局面 / 新开局满 32 子 / **对方恰好走一步**（2 格变化且动的是对方棋子）放行；凭空少子、我方棋子乱动一律**不建局、不支招**。
3. 日志新增「一致性判定」与「与上一局面」两列，下次再出问题一眼看出放行为什么、拒绝为什么。

这是零秒级等待的本地计算，不是 v1.11 那种等 3 帧确认 + 节拍器退避。

### 顺手修掉「有时不管用」的另一半

- **重试竞态**：v1.16 外层和 `retryTapCapture` 各读一次时钟，边界处内层提前 return、外层却已 return → 会话不收场、无提示，要静默等 12 秒兜底。现在单一时钟判定 + 返回 Boolean，外层一律按结果决定是否收场。
- **窗口用尽必收场**：ROM 不产新帧时不再反复识别同一张缓存帧，明确提示「画面没认稳，再点一次」。
- **点按会话期间也刷新最近帧**：v1.16 只在空闲态刷新 `lastFrame`，点按一开始它就停更，兜底拿到的是点击前缓存帧。现在每真实帧只转一次像素并无条件刷新，bypass 与兜底共用同一帧。

### 取舍（如实说）

- 多一帧一致性确认，约 0.1 秒；换来「不按误检局面瞎指挥」。跳不过的识别、算招、语音初始化照旧。

## v1.16 更新内容（点一下就顺：不再反复点，箭头出来就念）

对着 21:29 那份真机诊断（38 次点按 / 508 行）逐条算了一遍，也把**原生层、识别层、渲染层、播报层**都读进上下文了。你说的两处别扭，都不是「抓帧慢」，是链路里两道多余的闸。

### 先说结论：抓帧其实一点都不慢

日志实测：**点击→取帧 13~29ms，YOLO 识别 126~251ms**。v1.14 的「点下去立即读屏幕」是生效的，帧来源（点击瞬间缓冲现取 / 点击后新采帧 / 最近屏幕帧兜底）也写得清清楚楚。原生层这边，仓库里 `app/src/main/cpp/` 只有 `nativeutil.cpp`（CPU 特性探测），YOLO 走 TFLite Java Interpreter，棋局合法性在 Kotlin `AssistBoard.validate`，棋力引擎是预编译的 `libpikafish*.so`（UCI 二进制、无源码）——**这条链上没有原生代码在拖慢取帧**。

### 别扭一：点了像没读屏幕 → 其实是读了但被扔了

**38 次点按，20 次（53%）被「单帧合法性门槛」当场判死**，只弹一句「这一帧没认清棋盘，再点一次」，用户就得连点 2~6 次：seq 1/2 失败、第 3 次才成；seq 8~13 连着 6 次失败。主观就是「点了他没去读」。

根因链：单帧 YOLO 偶尔漏/误检一个子 → `AssistBoard.validate` 报「两将照面 / 红帅数量异常 / 某子数量超限」×1 → `TapFrameGate.check` 一票否决 → 立刻收场。`forceCaptureFrame()` 用 `setSurface + resize` 强制产帧，抓到的又常是合成器过渡帧，误检率更高（强制帧 7/14 合法，缓冲帧 11/24 合法，都约 50%）。

校验本身没错（正是它挡住了「乱指挥」），错在**只给一帧机会**。

**改法**：点击后 **700ms 窗口内最多抓 3 帧**，逐帧过同一道合法性门槛，**第一帧合法就立刻建局支招**；全不合法才如实收场。这是毫秒级「再抓一帧找好帧」，**不是** v1.11 那种「连续 3 帧一致 + 节拍器退避」的秒级确认 —— 不查节拍器、不等帧差、不叫用户重点。日志同步写明第几帧、每条不合法的具体原因。

### 别扭二：箭头都画出来了还不念 → 切入点确实挂错了

逐行核对：

- `renderOverlay` 里只要 `line != null && fromIsOurs(...)` 就给 `arrowFrom/arrowTo` 赋值、**箭头当场画出来**，文案还标着「（暂定）」；
- 但 `TapSpeakGate.decide` 硬性要求 `mature=true` 才念，而 `mature = searchSettled || 最佳着连续稳定 ≥ SUGGEST_STABLE_MS(1200ms)`；
- 所以「算出来（箭头出现）」到「念出来」中间**白等 1.2 秒**，日志里成功会话耗时 1.4~8.3 秒，其中 7.3 秒、8.3 秒是 8 秒兜底硬撑出来的。

这 1.2 秒是 v1.11 为了防「暂定着法横跳乱念」加的，可 `alreadySpoke`（本轮只念一次）+「会话收场即 WAIT」（杜绝残留）两条早已能挡住横跳，让用户干等纯属多余。

**改法**：播报切入点从「定着」改到**「箭头出现」**——本轮第一条通过起点双保险的建议到达就念一次、立刻收场，后续引擎继续算只更新界面、不再念；同时把面板**锁定在念过的那招**，避免「念的是 A、箭头却变成 B」。日志新增「④ 箭头已画出」和「箭头出现→播报」耗时。

### 取舍（如实说）

首着即念，念到的是引擎较浅的第一条 PV，可能不是 1.2 秒后更优的着法。你要的是「算出来就给我读」，那就换快；`fromIsOurs` 双保险、合法性门槛、本轮只念一次、收场不残留全部保留，不会退回「乱指挥 / 多指挥」。面板锁定保证念的＝画的，不会出现两套着法打架。

v1.15 起签名已固定并加了出包前指纹硬门禁，本版同钥匙。**如果你现在还是 v1.14**：卸载后直接装 v1.16 即可（v1.15 可跳过），这是最后一次卸载；之后所有版本直接覆盖安装。

## v1.15 更新内容（签名固定：以后不用再卸载重装）

### 你问的是哪个没固定

> 你这个包是包名没固定，还是什么签名没固定，还是什么东西，我每次都要卸载了再安装，不能覆盖安装。

**是签名没固定。** 包名和版本号都没问题。

沙盒下载 Release 资产被网络策略挡住，所以加了一次性 `Signing audit`，让 GitHub 构建机去下载 cn-1.12 / cn-1.13 / cn-1.14 三个真实安装包，用 `apksigner` + `aapt` 读出来：

| 版本 | applicationId | versionCode | 证书 SHA-256（前 16 位） |
| --- | --- | --- | --- |
| cn-1.12 | `com.xqdk.chess` | 43 | `0526d0ed3b3f1b0…` |
| cn-1.13 | `com.xqdk.chess` | 43 | `fc43a60079ebd74f…` |
| cn-1.14 | `com.xqdk.chess` | 43 | `15c9480c6f8bd20…` |

**三个包三把不同的证书**，所以 Android 判定「不是同一个签名」，每次都要求先卸载。之前我说「固定签名、可直接覆盖安装」是错的，这里更正。

### 为什么没固定住

主流水线头部注释其实写着「release 构建回退 debug 签名」。`build.gradle.kts` 的 release 签名需要 `app/cchess.release.2026.jks` + `local.properties` 里两个密码；CI 里这些都没有，于是回退到 `signingConfigs.debug`，用 `$HOME/.android/debug.keystore`。虽然配过一个 `DEBUG_KEYSTORE_B64`，但恢复这一步管不住 gradle 的回退逻辑，全新 runner 每次生成一把新 debug 钥匙。而 CI 里的「打印签名指纹」**只是打印、没有比对**，漂移了照样发版。

### 这版怎么修

## v1.8 更新内容（历史：两维度识别设置）

**不是发包漏了步骤**：v1.7 的 CI 全绿、包也确实发出去了，问题在功能逻辑 —— **录屏跑起来之后再改「识别方式」，服务根本不认新配置**。

诊断日志（2026-11-15 16:25 导出）把链路写得很清楚：

- `16:23:00` 录屏启动时档位是「点按变招」→ 服务把识别闸口记成「关」；
- 用户在增强功能页反复切换，最后 `16:24:48` 切到「自动识别」；
- 但 `16:25:01` 的面板动作仍是 `识别方式=自动识别 闸口=关 会话=false`，点棋盘只变成「切候选」。自动识别档本该闸口常开，却一直是关的 —— **不点棋盘啥也不干，点棋盘也不出招**，看起来就是「用不了」。

根因是服务的 `autoRecognize` 只在点「开始屏幕识别」那一刻算一次，设置页 Toast 还老实写着「下次启动识别时生效」。配置写进去了，运行中的服务没跟着变。

**这一版做了三件事**：

1. **运行中改配置立即生效**。设置页改完直接通知服务重算闸口（写一条「档位同步」诊断），帧循环和每次点棋盘前再兜底对齐一次，最多一个 tick（≤700ms）也必然对齐。去掉「下次启动识别时生效」的常态提示 —— 只有服务确实没在跑时才说明。
2. **自动识别开着时点棋盘也有反应**。v1.7 自动档会直接拦掉点按会话；现在两个维度独立，开着自动识别点棋盘仍执行所选动作（含单帧直出），单帧会话卡住也有 3 秒兜底收场。
3. **识别设置重新设计**（针对「四个开关只能开一个」）：拆成两个**互不排他**的维度，可以同时设置、各管各的 ——
   - **① 不点棋盘时**：`自动识别（连续识别）` 独立开关，默认**关**（不点＝零识别 / 零推理 / 零支招 / 零朗读）。
   - **② 点棋盘时做什么**：三选一，`点按出招（这一帧直接算，推荐）` / `点按刷新` / `点按变招`，选中项显示「已选 ✓」并着色，不再是四个「开 / 关」按钮互相顶掉。
   - 页面顶部新增一行**「当前生效」**，例如 `当前：不点不动 ＋ 点棋盘出招`，一眼看懂两者组合。
   - 旧配置自动迁移：v1.5~v1.7 存过的「自动识别」档会转成 `自动识别=开 + 点按出招`，不会静默跳档。

**诊断也跟着说清楚**：配置变更写「旧值→新值（立即生效）」；新增「档位同步」事件记录闸口 `关→开`；导出头部写两个维度的组合，并注明「头部是导出时配置，服务启动态见『服务 onCreate』，运行中切换见『档位同步』」—— 避免再出现「头部写自动识别、onCreate 写点按出招」被误读成 bug。隐私边界不变。

**升级说明**：包名 `com.xqdk.chess` 与固定签名未变，v1.7 可直接覆盖安装，不丢配置。

### 5. 修复：点棋盘没反应 + 诊断日志终于有参考价值

**用户实测问题**：装 v1.4 后点悬浮窗棋盘没反应、原有支招也消失；附的旧诊断文件
`XQDK_语音诊断_20261115_140310.md` 只有 3 行 TTS 事件（服务 onCreate / 引擎枚举 / 导出），
完全看不出点按、识别、支招哪一步断了。

**根因**：v1.4 一点棋盘就 `tracker.reset()` + `resetSuggestionState()`，把已确认局面和
已有支招清空，还强制要求重新凑满确认帧数产出 `NEW_BOARD` 才支招。静止画面、识别器缺
模型或棋盘被遮挡时确认链迟迟凑不满，超时后整屏空白。

**修复**：

- 点棋盘**保留**已有局面与支招，先按当前局面立即支招一次 → 点一下必有反馈；同时开
  识别闸口跑一轮识别。
- 画面没变 → `SAME_BOARD` 立即收场；画面变了 → `NEW_BOARD` 用新局面再支招一次。
- 识别失败 / 6 秒超时 → 按当前局面兜底支招，绝不留空白，并提示「本轮未重新识别，
  已按当前局面重新支招」。会话超时从 10s 收到 6s。
- **不点棋盘仍是零识别 / 零推理 / 零支招 / 零朗读**，语义不变。

**诊断日志扩展到覆盖本分支全部改动链路**：配置快照（版本 / 包名 / 识别方式 / 各开关）、
面板动作（点棋盘是否派发到服务）、点按出招会话（启动 / 拒绝原因 / 首帧可用 / 完成 /
超时兜底）、识别闸口、识别帧丢弃原因去重、识别引擎加载与回退、棋盘确认、支招调度、
状态文案、配置变更、导出事件。导出文件 `XQDK_增强功能诊断_*.md`，头部带「诊断覆盖」
一行与当前识别方式。隐私边界不变：只记事件与配置状态，不记帧像素、FEN 内容、对局、
引擎 PV 明细或性能数据。

> 排查「点棋盘用不了」现在先看日志里三行：`面板动作`（手势到没到）、`点按出招`
> （会话开没开 / 首帧在不在）、`识别帧`（帧被谁拦下）。
