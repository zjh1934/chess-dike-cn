## v1.12 更新内容（把不必要的等待全砍掉，必要的一段不动）

对着 18:41 那份诊断日志把 20 次点按逐条算了一遍，也**再次逐行读了原作者和我自己两边的代码**。你三个判断全对：

### 1. 「花很长时间分清敌我」——完全没必要，是我搞错了

原作者 `ScreenAssistService` 里写得明明白白：

> `mySideIsRed()` 注释：**屏幕下方阵营＝我方，红在下＝我方执红**

而 `DetectionBoardMapper.detectOrientation()` 是用**单帧里帅/将的位置**推断朝向的（帅在画面下半 = STANDARD）。也就是说：**「我方是谁」从这一帧就已经定了，根本不需要等好几帧慢慢确认**。你说的「我方不管执红还是执黑都在棋盘下方」，正是原作者写死的假设。

v1.11 我让点按走了原作者的「连续 3 帧一致才确认」链 —— 那套是给**自动识别、画面会动、有走子动画**设计的。点棋盘那一刻棋盘不动，那一帧就是确定的，多帧确认纯属白等。更糟的是备用 YOLO 识别为了防发热，两次识别之间强制退避，日志里 206 行「YOLO 节拍器退避 / 恢复放行」交替刷屏（占整份日志 35%），3 帧硬生生被拉成 **1.4～11.6 秒**。

**20 次点按耗时：3.0～12.5 秒，中位约 6～7 秒。** 这就是你说的「延迟真的很高」。

### 2. 哪些延迟必要、哪些不必要（你问的「有必要就保留」）

| 环节 | 耗时 | 判断 |
| --- | --- | --- |
| 认这一帧 | 0.1～0.3 秒 | **必要**，保留 |
| 引擎算一招 + 等最佳着稳定 1.2 秒 | 1.2～2.4 秒 | **必要**，保留（这段是招法质量，跳了就回到「乱指挥」） |
| 系统语音初始化 | 首次约 0.2 秒 | **必要**，保留 |
| 连续 3 帧确认 + YOLO 节拍器退避 | 1.4～11.6 秒 | **不必要**，删掉 |
| 12 秒干等会话预算 | 最多 12 秒 | **不必要**，删掉 |

**优化后预计总延迟约 1.5～2.5 秒**，招法质量不变。

### 3. 「有时读、有时不读」——不是语音坏了

日志里 `⑤ 语音播报`、`speak SUCCESS`、`决策 朗读=true` **各 15 次，一一对应**，TTS 一次没坏。真正的问题是 **5 次超时**（seq 2/3/4/16/19）软件干等 12 秒后**啥也没给**，只提示「再点一次棋盘」。20 次里 5 次石沉大海 = 25%，就是你感觉的「有时不读」。

根因：会话 12 秒预算从「点下去」就开始算，前面多帧确认吃光了 8～11 秒，后面「等定着」根本没时间，到点直接空手收场。

### 这一版怎么改

- **回到单帧**：点棋盘就用那一帧识别一次，不查节拍器、不等停稳、不走多帧确认。
- **但把 v1.10/v1.11 修好的正确性全部留在单帧路径上**：合法性校验（认错的局面不支招）、我方由「屏幕下方」单帧定且一局锁死、按我方回合请求、起点双保险、一次点按只念定着一招。**不会退回「敌我不分 / 多指挥」**。
- **预算从「建局完成」起算**（8 秒），到点引擎还没稳但有最佳着 → **念一次并收场**，绝不空手。以后每一次点按都有反馈。
- **一键关闭录屏按钮**：原来把可用状态绑死在 Activity 的服务绑定上，绑定一断按钮就灰掉 / 点了只弹个 Toast —— 日志里连一条「来源=主页一键关闭录屏」都没有，说明点击压根没走到停止逻辑。现在用服务自身的全局引用兜底、按钮始终可点、点击必写诊断。
- 日志顺手修：「识别次数=0」的计数 bug（确认链没累加）、点按链路文案改回单帧口径、点按会话内不再刷 200 行节拍器退避。

### 打包前门禁新增 4 组断言

单帧合法性门槛、我方由屏幕下方单帧定、定着超时必给一招、一键关录屏绑定断开也能关 —— 连同原有门禁全绿才准出包。

## v1.11 更新内容（回到原作者代码基础上重做）

**按你的要求，先把上游 `Silva6c/chess-dike` v3.4 的源码拉下来逐行看了**，再对着你 18:05 那份诊断日志找病根。结论很直接：**问题不是识别不准，是我为了「快」把原作者那套防错机制整段绕过去了。**

### 原作者是怎么做的

上游 `ScreenAssistService` 里，每一帧识别结果都交给 `BoardTracker.onFrame()`：

- `if (!res.isValid()) return UNSTABLE` —— **局面不合法（棋子数/帅将异常）直接不认**；
- 连续 `confirmCount`（默认 3）帧完全一致才确认 `NEW_BOARD`，用 `movedSide` 从前后局面差分推断该谁走；
- 只有确认了才 `onBoardConfirmed()` → 重置建议状态 → 发**一次**支招；
- 引擎 `onSearchUpdate` 只跟踪最佳着法变化，`stableUcci` 稳定满 1200ms 或 `onSearchDone` 才标「定着 ✓」；那些「（暂定）」着法原作者只用来刷**界面**，界面刷新快本来没问题。

### 我这边错在哪

v1.7 起为了「点一下立刻出招」，另写了 `applyTapDirectBoard` 单帧旁路，**合法性校验、多帧确认、轮次推断全被绕过**；更要命的是 v1.0 加中文播报时把 `voiceSpeaker.onSuggestion()` 直接挂在 `renderOverlay` 末尾——上游每次刷 UI 都会调一次，于是引擎每条 info 行都变成「念一招」。

你日志里写得很清楚：

| 现象 | 日志证据 |
| --- | --- |
| 一次点按念好几招、来回横跳 | seq=19：`炮2平1` → `将5退1` → `马8进9`（暂定）→ `马8进9 ✓`，中间还夹 `QUEUE_FLUSH 覆盖上一段` |
| 认错的局面也照出招 | seq=21/22：`认出=true 合法=false 问题数=1` 仍「交给支招」，接着念了 5 招 |
| 没把握也照出招 | seq=20~25：`差分推不出·沿用旧值（不确凿） ⚠` 仍「轮到我方→可出招」 |
| 上一轮残留还在念 | 17:58:30 念 `炮8平7`、17:58:52 念 `卒9进1` 时，对应的点按会话早就收场了 |
| 点了却啥也不给 | seq=18 判「轮到对方→不出招」，你只能隔 2.5 秒再点一次 |

### 这一版怎么改（在原作者链路上做，不再自己另起一套）

- **删掉单帧旁路**，点棋盘改为打开一个短「确认窗口」：帧照常进 `tracker.onFrame`，**合法 + 连续一致确认**后才 `onBoardConfirmed → scheduleAnalysis`。非法帧、动画帧、抖动帧一律不出招，提示再点一次。
- **点棋盘＝该我走**：确认后按我方回合请求支招，我方阵营一局锁死；配合起点双保险，引擎只会出我方棋子的着法。不再出现「轮到对方→不出招」「⚠不确凿还硬出」。
- **播报与渲染解耦**：新增 `TapSpeakGate`，只在**本轮定着**时念**一招**；暂定着法、状态文案、空文本、本轮已念过、会话已收场，一律不念。会话收场后引擎再怎么出 info 也不会有残留播报。
- **会话生命周期改对**：点一下 → 确认窗口 → 等定着 → 念一招 → 收场。收场后闸口关，**不点棋盘依旧零识别、零推理、零支招、零朗读**。
- 延迟：确认窗口用短 burst 把 3 帧压到约半秒；引擎算一招、系统 TTS 初始化这些跳不过的照旧。多花的半秒换「只给你一招、且是认准了的一招」。

### 打包前门禁加 2 组断言

`TapChainTest` 新增：**一次点按只播一招**（暂定/状态/已念过/会外都不念）、**非法局面走原作者确认链不会被确认**。连同原有 5 节点链路 + 敌我 4 项，全绿才准出包。

## v1.10 更新内容（修「敌我不分 / 指挥我去动别人的棋」）

**先认错**：v1.9 把「快」做到了，却把「准」丢了。你反馈「支招非常快，但瞎指挥，还指挥我去动别人的棋」——查下来是我上一版留的坑。

**病根（三层叠一起）**：

1. **该谁走，永远按「红先」算**。v1.7 做单帧直出时，为了不等多帧确认，把 BoardTracker 的差分推断整个砍掉，`applyTapDirectBoard` 写死沿用 `tracker.redGo`（服务启动默认 true=红先）。走了几步之后轮次早该交替了，写进 FEN 的 `w/b` 还是错的。
2. **我方是哪一方，每一帧都在猜**。`mySideIsRed()` 直接读单帧识别出的朝向；你日志里 `识别引擎=yolo`（ONNX 主模型因版权未随包，走备用识别），备用识别对红黑上下更容易判反。一判反就「敌我不分」。
3. **本来有防线，但跟着一起反了**。渲染里早有「送子防线」`fromIsOurs()`（着法起点必须是我方棋子），可它校验用的正是那个判反的 `myRed` —— 对方（红方）棋子的着法就这么被画了箭头、念了出来。

**这一版怎么修**：

- **轮次客观推断**：新增 `TapTurnInference.inferRedGo()`，用「上一局面 → 这一帧」的差分判断刚走的是哪一方，照抄 BoardTracker 原有口径推出下一手是谁。**不含「我方是谁」的假设**，你自己走完再点也不会反。
- **我方阵营一局锁死**：首次建局按屏幕朝向认一次，之后不随任何单帧识别结果翻；只有满 32 子的新对局才重定（换边）。
- **送子双保险**：建议着法起点必须**同时**是「我方棋子」且「当前该走方」，任一不符一律不显示、不朗读。宁可提示再点一次，也绝不指挥你去动别人的棋。
- **轮到对方时明确不出招**：给一句「现在轮到对方走，等对方落子后再点棋盘」，不会把对方的预案念成给你的建议。
- **诊断补上「敌我判定」**：每次点棋盘写明「我方=红/黑、该谁走、轮次来源、朝向是否锁定」，一眼看出判没判反。
- **诊断跨会话落盘**（这轮日志暴露的）：之前日志只存进程内存，你手动关录屏 / 服务一重启，那次乱支招的点按链路全丢 —— 你导出的这份日志里只剩 onCreate、关闭、再 onCreate、打开设置、导出，**一条点棋盘都没有**。现在关键事件同步写到应用私有文件，导出时把重启前的历史一起带出来。高频刷屏状态类不入盘，一次点按约 15 行，不拖慢识别/支招。

**CI 门禁同步加 4 项断言**（打包前必须全绿）：轮次客观推断、我方锁定不翻、绝不指挥动别人棋、跨会话日志能带出历史。

**要说清的限定**：首次点棋盘时我方阵营仍按识别朝向定一次；如果那一刻备用识别恰好判反，本局会锁错，直到换新对局才重定。但轮次已客观推断，锁错时「轮到我方」多半判成 false → **不出招并提示**，不会再瞎指挥。另外 `识别引擎=yolo` 仍是备用识别（合规取舍），锁定 + 双保险就是为它兜底。

**升级说明**：包名 `com.xqdk.chess` 与固定签名未变，v1.9 可直接覆盖安装，不丢配置。

- **延迟**：保留 v1.7 的单帧直出（不等停稳、不凑多帧确认、不查节拍器、不拿旧招兜底）；识别 + 引擎搜索 + 系统 TTS 初始化这些跳不过的照旧，不额外加等待。

## v1.8 更新内容（历史：两维度识别设置）

**不是发包漏了步骤**：v1.7 的 CI 全绿、包也确实发出去了，问题在功能逻辑 —— **录屏跑起来之后再改「识别方式」，服务根本不认新配置**。

诊断日志（2026-11-15 16:25 导出）把链路写得很清楚：

- `16:23:00` 录屏启动时档位是「点按变招」→ 服务把识别闸口记成「关」；
- 用户在增强功能页反复切换，最后 `16:24:48` 切到「自动识别」；
- 但 `16:25:01` 的面板动作仍是 `识别方式=自动识别 闸口=关 会话=false`，点棋盘只变成「切候选」。自动识别档本该闸口常开，却一直是关的 —— **不点棋盘啥也不干，点棋盘也不出招**，看起来就是「用不了」。

根因是服务的 `autoRecognize` 只在点「开始屏幕识别」那一刻算一次，设置页 Toast 还老实写着「下次启动识别时生效」。配置写进去了，运行中的服务没跟着变。

**这一版做了三件事**：

1. **运行中改配置立即生效**。设置页改完直接通知服务重算闸口（写一条「档位同步」诊断），帧循环和每次点棋盘前再兜底对齐一次，最多一个 tick（≤700ms）也必然对齐。去掉「下次启动识别时生效」的常态提示 —— 只有服务确实没在跑时才说明。
2. **自动识别开着时点棋盘也有反应**。v1.7 自动档会直接拦掉点按会话；现在两个维度独立，开着自动识别点棋盘仍执行所选动作（含单帧直出），单帧会话卡住也有 3 秒兜底收场。
3. **识别设置重新设计**（针对「四个开关只能开一个」）：拆成两个**互不排他**的维度，可以同时设置、各管各的 ——
   - **① 不点棋盘时**：`自动识别（连续识别）` 独立开关，默认**关**（不点＝零识别 / 零推理 / 零支招 / 零朗读）。

   - 页面顶部新增一行**「当前生效」**，例如 `当前：不点不动 ＋ 点棋盘出招`，一眼看懂两者组合。
   - 旧配置自动迁移：v1.5~v1.7 存过的「自动识别」档会转成 `自动识别=开 + 点按出招`，不会静默跳档。

**诊断也跟着说清楚**：配置变更写「旧值→新值（立即生效）」；新增「档位同步」事件记录闸口 `关→开`；导出头部写两个维度的组合，并注明「头部是导出时配置，服务启动态见『服务 onCreate』，运行中切换见『档位同步』」—— 避免再出现「头部写自动识别、onCreate 写点按出招」被误读成 bug。隐私边界不变。

## v1.7 更新内容（顺手版 · 历史）

这一版按真机诊断日志和反馈，只解决「用起来不顺手」，并补一个主页按钮：

- **点棋盘 = 这一帧直接算**：不再等画面停稳、不再凑连续 3 帧确认、不再被节拍器拉开间隔、不再 6 秒超时拿旧招兜底。点下去就用点击前最近那一帧识别一次 → 立刻按这个局面支招并播报，当场收场；认不出来就明说「这一帧没认清棋盘，再点一次」。**不点棋盘仍是零识别 / 零推理 / 零支招 / 零朗读**。

### 5. 修复：点棋盘没反应 + 诊断日志终于有参考价值

**用户实测问题**：装 v1.4 后点悬浮窗棋盘没反应、原有支招也消失；附的旧诊断文件
`XQDK_语音诊断_20261115_140310.md` 只有 3 行 TTS 事件（服务 onCreate / 引擎枚举 / 导出），
完全看不出点按、识别、支招哪一步断了。

**根因**：v1.4 一点棋盘就 `tracker.reset()` + `resetSuggestionState()`，把已确认局面和
已有支招清空，还强制要求重新凑满确认帧数产出 `NEW_BOARD` 才支招。静止画面、识别器缺
模型或棋盘被遮挡时确认链迟迟凑不满，超时后整屏空白。

**修复**：

- 点棋盘**保留**已有局面与支招，先按当前局面立即支招一次 → 点一下必有反馈；同时开
  识别闸口跑一轮识别。
- 画面没变 → `SAME_BOARD` 立即收场；画面变了 → `NEW_BOARD` 用新局面再支招一次。
- 识别失败 / 6 秒超时 → 按当前局面兜底支招，绝不留空白，并提示「本轮未重新识别，
  已按当前局面重新支招」。会话超时从 10s 收到 6s。
- **不点棋盘仍是零识别 / 零推理 / 零支招 / 零朗读**，语义不变。

**诊断日志扩展到覆盖本分支全部改动链路**：配置快照（版本 / 包名 / 识别方式 / 各开关）、
面板动作（点棋盘是否派发到服务）、点按出招会话（启动 / 拒绝原因 / 首帧可用 / 完成 /
超时兜底）、识别闸口、识别帧丢弃原因去重、识别引擎加载与回退、棋盘确认、支招调度、
状态文案、配置变更、导出事件。导出文件 `XQDK_增强功能诊断_*.md`，头部带「诊断覆盖」
一行与当前识别方式。隐私边界不变：只记事件与配置状态，不记帧像素、FEN 内容、对局、
引擎 PV 明细或性能数据。

> 排查「点棋盘用不了」现在先看日志里三行：`面板动作`（手势到没到）、`点按出招`
> （会话开没开 / 首帧在不在）、`识别帧`（帧被谁拦下）。
